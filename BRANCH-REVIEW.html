Core storage engine

Reviewer verdict: request-changes

What changes

  • The SST format moves to v2: every data, index and Bloom block now ends in a CRC-32 trailer, the reader accepts v1 and v2, a failed checksum or a block that ends mid-entry is Error::Corrupt instead of a silent miss, footer- and index-declared lengths are bounds-checked before allocation, and reads are positional (pread/seek_read) on a shared File rather than seek+read under a Mutex.
  • Compaction no longer loads every run into one BTreeMap: Sst::entries sweeps a run block by block outside the block cache, MergeIter performs a heap k-way merge in (table, key, seq DESC) order with the later run winning ties, and GcIter streams version reclamation straight into sst::write_sorted; the merged run is stamped with the newest input max_seq rather than the newest surviving entry, which also fixes a sequence regression on restart when the newest entry of an all-dead key was reclaimed.
  • The memtable flush writes and fsyncs its SST under the store read lock and takes the write lock only for the swap; the argument (memtable mutable only inside durable_commit, which the write gate serializes) holds because NativeWriteTxn owns the WriteGuard for its whole life and apply_replicated and commit_at_least both acquire the same gate.
  • durable_commit now returns Ok once the batch is fsynced and published; a failure in the flush/compaction it triggers is logged and parked in NativeEngine::last_maintenance_error (cleared by the next successful pass) instead of failing a commit whose write already landed, and the API/web layers expose that slot.
  • Directory fsyncs are added after an SST rename, after the WAL truncation, after compaction's unlinks, and once when a store is created; the WAL cursor is rewound before the truncation fsync so a failed fsync cannot leave later batches behind a zero hole; WAL record length is checked against u32::MAX before any byte is written.
  • apply_replicated refuses a batch whose seq is at or below committed_seq with Error::Conflict, and snapshot restore lands via commit_at_least(max(next, snapshot seq)) so a fresh replica adopts the master's sequence and the next live batch is accepted.
  • HNSW remove hands the entry role to the tallest live node and lowers top_layer to match (the old arbitrary successor could panic on the next query because search indexes layers[top_layer] unchecked); search borrows a per-thread scratch taken out of its RefCell for the duration and retained only under a 16 MiB cap.
  • The graph layer's bulk loader now rejects an external key already owned by a node in the plane, and delete_node removes the ext_keys row only when it still points at the node being deleted.
  • One durability regression was found: compaction unlinks the merged-away runs newest first, which is the order that can leave an older run's put on disk with neither its tombstone nor the merged run shadowing it; master's oldest-first order was the safe one and arch/01 now documents the inverted reasoning.

Strengths

  • sst.rs read_block_at/checked_len/next_entry (crates/dr-strange-core/src/storage/native/sst.rs ~lines 414-580): every footer- and index-declared length is bounded by the file/data region before a Vec is allocated, only verified payloads enter the block cache, and corruption in any layer (footer magic, index, bloom, data) surfaces as Error::Corrupt with a test per layer (v1_block_ending_mid_entry_is_corrupt_not_absent, v2_flipped_byte_in_data_block_is_corrupt, v2_index_and_bloom_are_checksummed, unknown_magic_and_out_of_range_blocks_are_corrupt).
  • MergeIter's ordering (crates/dr-strange-core/src/storage/native/mod.rs, MergeHead::cmp) encodes 'later run wins' in the heap key and dedups via last, and the_streaming_merge_equals_the_map_merge_and_the_later_run_wins pins it against the old BTreeMap union including a cross-run duplicate; a_failing_sweep_ends_the_merge_with_its_error proves an I/O error aborts the output file instead of producing a truncated run.
  • Stamping the merged run with max of input max_seq (mod.rs maybe_compact) quietly fixes a case the old code got wrong: when GC dropped the newest entry overall, committed_seq on reopen could fall below a sequence already handed out.
  • a_reader_is_served_while_a_flush_writes_its_sst, commits_after_a_failed_wal_truncation_fsync_start_at_offset_zero and a_commit_is_ok_once_durable_even_when_the_flush_it_triggers_fails (mod.rs engine_tests) each fail on master's code paths; the injected-fault seams replace chmod-based tests that root and Windows ignore.
  • hnsw.rs search: the scratch is moved out of the thread-local rather than borrowed across the search, there is no fallible operation between take and put-back, and shared_search_scratch_does_not_leak_between_indexes checks the generation stamp against a fresh-thread oracle; removing_the_entry_node_keeps_the_graph_wellformed walks the successor chain through every layer height.
  • graph/node.rs delete_node and graph/bulk.rs stage_nodes: the ownership check is the same point get create_node_with_key already does, the bulk batch is fully staged before any write so a Conflict leaves the plane untouched, and both tests (deleting_a_node_leaves_another_nodes_ext_key_row_alone, bulk_load_rejects_external_key_owned_by_existing_node) fail without the change.

high Compaction unlinks merged runs newest-first, the order that can resurrect a GC'd put

crates/dr-strange-core/src/storage/native/mod.rs:641 · durability · confirmed

Claim. maybe_compact deletes the runs it merged with old.iter().rev() (newest first). Because reads walk store.ssts.iter().rev() and on reopen sst::list orders by number so the merged run is consulted first, a crash (or a failing remove_file) after the newer run is gone but before the older one is leaves [older run with put K, merged run with K reclaimed] on disk and K comes back with nothing shadowing it; the next compaction then writes that put into the bottom run permanently. The safe order is oldest first, which is what master did (old.iter()); the comment above and arch/01 §6.1 state the inverted rationale.

Evidence. R1 = sst-000001 {put K@5}, R2 = sst-000002 {del K@9}, min_snapshot >= 9 so emit_group drops K entirely from M = sst-000003. paths = [R2, R1]; remove_file(R2) succeeds, then power loss or remove_file(R1) -> Err (EIO/EPERM, which `?` propagates and record_maintenance swallows). Reopen: list = [R1, M]; get(K) checks M (absent) then R1 -> Some(put K@5). With oldest-first, any prefix removed leaves [Rk..Rn, M] where every tombstone shadowing a put in Rk..Rn is in some Rj (j>=k) or in M, so no shape resurrects.

Suggested fix. Iterate old in stored order (drop .rev()): `let paths: Vec<PathBuf> = old.iter().map(|s| s.path.clone()).collect();`. Rewrite the comment to say oldest first: a tombstone always lives in a run at least as new as the put it kills, so removing oldest-first never drops a tombstone before its put. Fix arch/01 §6.1 line 249 ('newest first') accordingly. Optionally add a test that opens a directory holding [R1 with put, M without the key] and asserts the merged file order/read path, or at least a unit test over the paths vector order.

Verifier note (confirmed)

The code path is exactly as claimed. `crates/dr-strange-core/src/storage/native/mod.rs:641` builds `paths` from `old.iter().rev()` (newest run first), a change from master's `old.iter()` (diff confirms). `emit_group` (mod.rs:~862-870) truncates a group to the first version at/below `min_snapshot` and then drops a lone `Del` at/below the floor, so for R1={put K@5}, R2={del K@9}, min_snap>=9 the merged run M contains no entry for K. `open` (mod.rs:~364-369) rebuilds `store.ssts` purely from `sst::list` (sst.rs:797-813), which sorts by file number with no manifest, so a directory left as [sst-000001 (R1), sst-000003 (M)] loads as [R1, M]; `committed_get` (mod.rs:1526) walks `ssts.iter().rev()`, finds nothing in M and returns R1's put — K is resurrected. With oldest-first removal, every reachable prefix state [Rk..Rn, M] still holds each tombstone in a run at least as new as its put, so no resurrection is possible; the comment above line 641 and arch/01-storage.md:249 state the inverted rationale.

Verifier note (confirmed)

The code path is as described. `write_sorted` creates `path.with_extension("tmp")` (crates/dr-strange-core/src/storage/native/sst.rs:272-273) and only renames at sst.rs:350; there is no cleanup on the error path either (e.g. a merge iterator `Err` mid-write, exercised by the test at mod.rs:1088, aborts and leaves `sst-000001.tmp` behind). Test coverage

Coverage for the risky changes is strong and each new engine, SST and HNSW test was checked against the pre-change code path and would fail there: the parked-flush reader test times out under the old write-lock flush, the WAL-cursor test observes the zero hole, the injected-flush-failure test observes the old Err, the SST corruption tests observe the old Ok(None), the entry-removal test panics on the old arbitrary successor, and the graph tests observe the stripped ext_keys row. The streaming merge is pinned against the BTreeMap union including a cross-run duplicate and an error mid-sweep.

  • No test covers compaction's unlink order or a remove_file failure mid-loop followed by reopen; this is exactly where the one high finding lives. A directory-level test (write R1 {put}, R2 {del}, force a compaction, then simulate the partial unlink by recreating the file layout and reopening) would have caught it.
  • No test opens a directory containing a leftover sst-NNNNNN.tmp or a v1 run alongside v2 runs and then compacts (the doc says a v1 run is rewritten as v2 by the next compaction; only the isolated v1 open/read is tested).
  • The directory fsyncs (sst::write, maybe_flush, open) are untested and untestable in-process; they are also unix-only by design, which the doc states.
  • The compaction path is only exercised through the 1-byte-threshold engine test and gc_tests; there is no test that compaction after a failed compaction (merged file already renamed, swap not done) reuses the number safely, although reading the code shows it does because next_sst is bumped only in the swap.

Residual risks and open design questions

  • Compaction still merges every run once the count exceeds COMPACTION_TRIGGER, so each pass rewrites the whole on-disk set; streaming bounds memory, not I/O.
  • A single rotted block in any run fails every subsequent compaction with Corrupt; the failure is now visible through last_maintenance_error/check, but the engine does not quarantine the run and the run count keeps growing until an operator intervenes.
  • Removing the HNSW entry node costs a linear scan over the live set; a workload that repeatedly deletes the current entry pays O(N) per delete.
  • The bulk loader now issues one ext_keys point get per keyed node, the same cost as the per-record path; very large keyed batches pay it in full.
  • Range reads still materialise the requested range per run into a BTreeMap per call (documented as unchanged).
  • Directory fsyncs and the crash-ordering guarantees are unix-only; on Windows the code relies on NTFS metadata journaling, as the doc states.
  • The thread-local search scratch is retained per thread up to 16 MiB; a large blocking pool that searches a 4M-node index pins up to 16 MiB per thread by design.

Core API, cache and compute

Reviewer verdict: approve-with-nits

What changes

  • `Database::init` now reads first and commits only when magic, format version or a plane's counters row is missing, so reopening an initialised database (and every restart of a read-only replica) no longer advances the commit sequence; `needs_bootstrap` mirrors exactly what `graph::init` would write.
  • `WriteTxn::commit` returns `Ok` once the KV is durable: every buffered vector event is attempted, failures are logged and counted, and a sticky `indexes_diverged` flag makes `save_sidecars` withhold and remove the `.hnsw` sidecar and `snapshot` embed a fresh rebuild, so a diverged HNSW registry is never persisted at the current sequence.
  • `drop_plane` now deletes the plane's vector/keyword declarations from `meta` and the matching live registry entries; `restore` loads the shipped index frames into the live registries (in-memory databases included), falls back to a rebuild from the KV, recounts per-plane counters, lands the snapshot's sequence via `commit_at_least` so a fresh replica accepts the master's next batch, and treats a failed sidecar write as a warning.
  • `apply_replicated` drops the graph cache after every batch and mirrors the batch into the follower's HNSW/BM25 registries by re-deriving each written node row from the landed KV (a declaration change rebuilds both registries, a plane tombstone drops theirs).
  • The L2 cache keys entries by `(plane, id)`, refuses entries heavier than min(4 MiB, budget/16), and carries a generation token captured before a reader opens its snapshot; `invalidate_all` bumps the generation before clearing so a reader straddling a restore or replicated batch cannot repopulate the cache under a reused sequence. `record_query` commits unstamped so history rows no longer flush the cache.
  • Index hits the reader's snapshot cannot decode (or that lost the queried label) are dropped in `visible_hits` for both readers; AS OF keyword and hybrid-keyword searches compute BM25 from the pinned snapshot via `KeywordRegistry::search_snapshot`, and the same snapshot path is now the `UncachedReader` oracle with a differential test against the live registry.
  • The executor pulls `ExpandVar` lazily (same preorder as before) so `Limit` and the deadline bound exponential walks, ranks `FrontierTopK` over distinct heads while keeping each winner's first trail, and saturates plan counts to `usize`; hybrid fusion drops non-finite channel scores, sorts with `total_cmp`, and scores the graph channel only on nodes carrying the queried label. The catalog build decodes each node once and the change feed is capped at the source.
  • The JSON dialect rejects integers above `i64::MAX` instead of wrapping them and wraps maps with `$`-prefixed keys in a `{"$map": …}` escape so they round-trip; arch/02, 03 and 04 are updated to describe all of the above.

Strengths

  • The generation token in `crates/dr-strange-core/src/api/cache/store.rs` (captured in `PlaneHandle::with_reader` at `crates/dr-strange-core/src/api/mod.rs:1244` before the snapshot opens) is the right shape for the foreign-sequence problem, and both the straddling-reader unit test and the restore/replicated-restore tests in `crates/dr-strange-core/src/api/snapshot.rs` would fail without it.
  • Making `KeywordRegistry::search_snapshot` (`crates/dr-strange-core/src/keyword.rs`) the single way an index is built from the KV, and using it as the `UncachedReader` oracle with `indexed_keyword_search_matches_the_snapshot_oracle`, gives the live BM25 path an exact differential check it did not have before.

  • `needs_bootstrap` (`crates/dr-strange-core/src/api/mod.rs:971`) checks precisely the three things `graph::init` and the counters backfill would write, and `reopening_a_replica_writes_nothing_so_its_sequence_stays_the_masters` pins the replica consequence end to end.

Verifier note (confirmed)

The code path holds as stated. `ReplicatedIndexWork::from_ops` (crates/dr-strange-core/src/api/mod.rs:2390-2403) does `!work.nodes.contains(&key)` on a `Vec<(PlaneId, NodeId)>` for every `TableId::Nodes` op, which is a linear scan per op and therefore O(n²) over the batch. low Generation check and moka insert are not atomic; a stale insert can land after invalidate_all

crates/dr-strange-core/src/api/cache/store.rs:112 · durability · confirmed

Claim. `GraphCache::insert` reads the generation, compares, and then calls `self.cache.insert`; an `invalidate_all` that runs between the comparison and the insert neither refuses nor wipes the entry, contradicting the guarantee stated in the `invalidate_all` doc comment (line 127) and arch/02 §3.

Evidence. moka 0.12's `invalidate_all` only guarantees that entries inserted before or at the invalidation time are not returned (sync/cache.rs doc: 'guaranteed not to return the entries inserted before or at the invalidation time'). Interleaving: reader thread evaluates `generation == self.generation()` → true (g0); restore thread runs `fetch_add` (g1) then `cache.invalidate_all()`; reader thread resumes and executes `self.cache.insert(key, value)` with a timestamp after the invalidation. The pre-restore record is now cached under the restored seq and served to every later reader at that seq until the next graph write bumps it. The window is a few instructions wide and only matters when the foreign commit reuses a seq already stamped, but the branch added the generation precisely to close that window.

Suggested fix. Double-check after the insert: `self.cache.insert(key.clone(), value); if generation != self.generation() { self.cache.invalidate(&key); }`. Either the clear saw the entry (timestamp before) or the post-check sees the bumped generation and removes it. Adjust the doc comment accordingly.

Verifier note (confirmed)

The code path is exactly as described. `GraphCache::insert` (crates/dr-strange-core/src/api/cache/store.rs:111-115) does `if weight(..) <= cap && generation == self.generation() { self.cache.insert(key, value); }` — a check-then-act with no atomicity between the compare and the moka insert. `invalidate_all` (store.rs:127-130) does `fetch_add` then `cache.invalidate_all()`, and moka 0.12.15's `invalidate_all` (~/.cargo/registry/.../moka-0.12.15/src/sync/cache.rs:1646-1648) only records the current time and hides entries inserted "before or at" that time; an insert that executes after it is retained. So the interleaving reader-compare(true) -> restore fetch_add + invalidate_all -> reader `cache.insert` leaves a pre-restore record stamped with the pre-restore seq in the cache. Both callers (`Database::restore` at api/snapshot.rs:376 and `apply_replicated` at api/mod.rs:586) run while readers can have open snapshots (`with_reader` at api/mod.rs:1244 captures the generation before `with_read`, and nothing serialises readers against these paths), so the race is reachable. It only becomes visible when the foreign seq equals the seq the stale entry was stamped with, and the window is a handful of instructions, which is why I would rate it low rather than medium — but the doc comment at store.rs:124-126 ("either refused ... or wiped ... The other order would let one slip in between") asserts a guarantee the code does not provide. The suggested post-insert re-check (`insert; if generation != self.generation() { self.cache.invalidate(&key) }`) does close it: either the clear's timestamp is >= the insert's (entry hidden) or the post-check observes the bumped generation and removes it.

Cypher parser and compiler

Reviewer verdict: approve-with-nits

What changes

  • The lexical surface now matches the docs: identifiers are Unicode words or anything between backticks, strings in either quote style take the openCypher escapes (an escaped quote can no longer end a literal), floats accept an exponent, and keywords and function names are case-insensitive.
  • Expression nesting is bounded by a thread-local RAII counter (parse.rs `descend`/`Nesting`, MAX_NESTING = 64); parentheses, NOT, unary minus and every operator of an AND/OR/arithmetic chain each cost one level, so ten thousand parentheses or a hundred-thousand-conjunct chain is a syntax error rather than a stack overflow anywhere downstream.
  • Shapes openCypher allows but this cut cannot run (second MATCH, OPTIONAL MATCH, WITH, UNION, UNWIND, multi-path patterns, relationship variables, inline MATCH properties, list/map literals as values, `%`/`^`) now fail hard at the point of recognition with a rewrite hint surfaced as ParseError::Compile; write clauses commit after their keyword and the two readings of a MATCH are compared by how far they got, so errors point at the fault instead of token 0.
  • The compiler places variable-free predicates and any conjunct that reads `hops()`/`score()` on the last slot (reading earlier variables through `Expr::At`), so `hops() = 2` no longer silently drops every row; `<>`, `NOT`, and `=` with no constant side are wrapped in `IS NOT NULL` guards on the properties they read so a missing property satisfies neither a test nor its negation; `IN` lists expand to a balanced OR tree.
  • `ORDER BY count(*)` (and any aggregate) resolves to the projected column that folds the same way regardless of alias or spelling, with a clear error in node-returning queries.
  • The write path runs its MATCH with `Step::Distinct` (dedupe by terminal node id) so a node reached by two paths is mutated once; MERGE consults a statement-scoped set of staged edges and the keys CREATE registered, so it is idempotent against the same statement; `{key: $param}` is resolved and type-checked before any row runs.
  • The completer walks characters instead of bytes, reads escaped strings and backticked names the way the parser does, tokenises exponent floats, models a CREATE/MERGE property map as its own region, and refuses to complete past an inline map in a MATCH node; the grammar hint gained a lexical section.
  • Algorithm arguments keep the user's case for property names (only `dir` is lowercased) and refuse counts that do not fit u32 instead of truncating.
  • The English and Chinese query-language docs gained sections on missing properties, literals/identifiers, the nesting limit and the unsupported list; they match the code except for the IN-with-null claim noted below.

Strengths

  • parse.rs `descend`/`Nesting`: the depth counter is an RAII guard, so backtracking and early `?` returns keep it exact, and the chain-charging keeps the returned tree depth within ~2x MAX_NESTING for every consumer (split_and, compiler, drop glue); tests/parse.rs exercises 10,000-deep parentheses and 100,000-operator chains in WHERE, RETURN, ORDER BY and a write's WHERE.
  • parse.rs hard-failure discipline: `unsupported`, `escape` and `descend` return nom::Err::Failure so no enclosing `alt` re-reads the text; `return_item` now propagates a Failure from the aggregate argument instead of falling through to the bare-variable reading; I checked every `if let Ok`/`while let Ok`/`is_ok()` site and each wraps a combinator (kw, symbol, ident, *_op, uint) that cannot hard-fail, so no unsupported message or nesting failure is ever swallowed.
  • compile.rs `balanced`: the IN expansion is a balanced tree, and tests/parse.rs compiles a 100,000-item IN and NOT IN into one step.
  • write.rs: the dedupe relies on core's `Step::Distinct`, which keys on `row.head` (exec.rs:559), so two different anchors reaching the same terminal node still collapse to one mutation; `StagedEdges` plus `merged.insert` in `get_or_create` closes the CREATE-then-MERGE and self-crossing-path cases, each pinned by tests/write.rs with edge counts.

  • complete.rs: tests/complete.rs cuts a multibyte query at every character boundary and asserts no panic, which is the right test for the byte-to-char rewrite.

Residual risks and open design questions

  • A same-host reverse proxy that adds no `Forwarded`/`X-Forwarded-*`/`Via` header and rewrites `Host` to a loopback value (nginx's default `proxy_set_header Host $proxy_host` does exactly this) is indistinguishable from a local browser: the page still carries the token and a typed loopback `Origin` still earns the tokenless fallback. The docs say to set `DRSG_PAGE_TOKEN=0` and a token; the default is not safe for that shape.
  • The throttle keys IPv6 clients by full address, so a client with a /64 has five free guesses per address; the table's eviction bound (4 096) means a rotating flood also evicts other peers' strikes. Documented as 'weakens the throttle for that flood and nothing else', which is accurate.
  • `/snapshot` now writes a whole-database image into the OS temp directory per request (tmpfs on many hosts, so RAM again) and concurrent followers each get their own copy; a spool failure is a 500 before the status line, which is the right failure but a new disk dependency.
  • A streamed `/export` holds one blocking-pool thread for the client's entire download, and tower's concurrency limit releases its permit when the response headers are produced, so N slow readers occupy N blocking threads outside `max_concurrent`.
  • `/export` is not a consistent snapshot: ids are scanned once and records read individually, so an edge to a node created after the id scan can be emitted without its endpoint line (same class of behaviour as before the branch).
  • A degree-ordered `graph.seed` ranks only the first 20 000 nodes in scan order, and each scan page still costs an O(plane) id collection in the core; both are stated in arch/08 as open items for a resumable cursor.
  • The follower's pull-time backlog is bounded in ops, not bytes; a master committing large property blobs during the pull can still hold substantial memory before the forwarder stops reading.
  • `digest.run` with `apply: true` remains ungated over JSON-RPC by explicit decision (arch/08 §4.1 item 8), so any holder of the write token can rewrite a plane in one call.

Method and limits

  • Eight independent read-only reviewers, one per area, read the full diff master...HEAD for their paths, the surrounding code and the tests; the eighth assessed commit hygiene, CHANGELOG accuracy and docs consistency rather than code.
  • Every finding was handed to a separate verifier instructed to refute it against the branch; only confirmed and uncertain findings appear in the body, refuted ones in Appendix A. Severity shown is the verifier's when it confirmed.
  • Reviews are static: nothing was executed beyond the gate listed above. Concurrency and crash-consistency claims rest on reading, not on fault injection beyond what the branch's own tests do.
  • The reviewers did not re-audit master; pre-existing issues are reported only when the branch touches them.
